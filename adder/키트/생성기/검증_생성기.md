## 5. 명세가 사람이 고칠 만한 형식인가

- **한 줄에 행 하나는 맞는 선택이다.** 1,211줄 가운데 줄 길이의 중앙값 144자 · 90%가 584자 안. 수식 하나를 고치면 diff 가 두 줄(−/+)이고 읽힌다. 줄 이름 하나를 고치고 `다시쓰기` 를 돌리면 다섯 파일 15줄이 바뀐다(덧붙인 이름). JSON 을 읽어 그대로 다시 써도 바이트가 같고 `다시쓰기` 는 고치지 않은 명세를 한 글자도 안 바꾼다.
- **긴 줄이 문제다.** 500자를 넘는 줄 150 · 1,000자를 넘는 줄 42 · 가장 긴 줄 9,933자(13번) · 7,030자(12번 점검 줄). 이런 줄은 diff 로 어디가 바뀌었는지 못 읽는다. 옛 스캐폴드의 긴 판정 수식과 안내 글이 그대로 온 것이므로 3단계에서 점검을 15번으로 모으고 안내 글을 빼면 줄지만, 형식 쪽에서도 `무늬` 를 줄바꿈해 적는 꼴(한 행을 여러 줄 JSON 으로)이나 긴 수식을 이름 붙인 조각으로 나누는 수단을 둘 만하다.
- **수식 속 큰따옴표가 `\"` 로 적힌다.** 글을 내는 수식(733칸)은 읽기 어렵다. JSON 을 쓰는 한 피할 수 없다.
- **주석을 달 곳이 없다.** `//` 줄은 JSON 오류이고, 모르는 열쇠(`"주석"`)는 무시되다가 `다시쓰기` 에서 사라진다. 산식을 고치는 사람이 「왜」를 적을 자리(`"메모"` 열쇠)가 필요하다. 새 줄의 높이를 적을 열쇠도 없다(옛 서식 파일에만 있다).
- **덧붙인 이름이 안내 글인 줄**이 있다 — `[$S12R028 22행 종료일만 내 평가기준일에 맞추면 24]`. 이름표가 줄 이름을 고치면 풀린다(구현자도 적었다).
- 열쇠의 차례가 줄마다 다르다(`id · 단위 · 이름` / `id · 이름 · 단위`). 단위가 수식이면 먼저 나온다. 고정하는 편이 읽기 좋다.
- 문법 자체(`[ID 이름]@열`)는 읽힌다. `@.` 과 `@-1` 의 구별, `@예측` · `@예측.끝` 은 설명서대로 움직였다. 걸리는 것은 문법이 아니라 **점검의 세기**다 — 틀린 ID · 틀린 별칭 · 틀린 순서가 대부분 통과한다.

```
python 실험_시나리오.py                               # 스위치 비관·낙관에서 값 대조(2-4)
python 실험_돌연변이.py                               # 구조 대조의 돌연변이 일곱 갈래(2-3)
python 실험_훑기.py                                   # 지금 명세에 걸리는 곳이 있는지(3-4)
python 지문.py <낼 json>                              # 원본 폴더의 크기·시각·해시
```

엑셀을 쓰는 스크립트는 `실험공통.엑셀재계산`(`DispatchEx` · 자기가 연 통합문서만 닫고 자기가 띄운 엑셀만 `Quit`)만 쓴다.
